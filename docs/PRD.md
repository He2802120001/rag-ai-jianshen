# **健身问答助手 需求说明（PRD）**

## **1. 项目一句话**

面向健身入门者的文档问答助手，基于 RAG 回答动作技术、一般营养原则和伤病预防问题；对伤病诊断、用药、疾病饮食和特殊人群建议明确拒答并引导就医。

## **2. 背景与目标**

健身入门者常在网上查到互相矛盾、质量参差的内容，且难以判断哪些建议对自己不安全。本项目把可控的科普文档整理成知识库，提供一个**有引用、有边界、可评估**的问答入口。

目标不是做“健身百科”，而是验证三件事：

1. 垂直领域文档经 RAG 后能否给出可溯源的回答；
2. 不同风险等级的内容能否用分层路由区别处理；
3. 系统在“不该答”的问题上能否稳定拒答，且不过度误拒正常问题。

## **3. 目标用户**

- 刚开始健身、需要查动作要领和基础营养知识的人；
- 能判断“这个回答有没有引用来源”的普通用户；
- 不面向需要康复治疗、疾病管理或专业训练计划的人群。

### **4.2 不可答范围（安全边界）**

以下问题**不检索、不生成训练或饮食建议**，统一返回引导话术，建议咨询医生、康复师或注册营养师：

- 具体伤病的诊断、治疗、康复方案（如“腰椎间盘突出能不能硬拉”“膝盖疼怎么治”）；
- 用药相关问题；
- 疾病相关饮食（糖尿病、肾病等）；
- 特殊人群的训练与饮食建议（孕妇、心血管疾病患者、术后人群等）；
- 超出健身科普范围的医疗问题。

### **4.3 模糊问题**

问题信息不足时（如“我该怎么练”），先追问澄清，不直接给泛化建议。

## **6. 非功能需求**

- **安全**：API Key 存环境变量；后端只监听 127.0.0.1，由 Nginx 反向代理；HTTPS。
- **可评估**：每次修改检索策略或提示词后能重跑评估集并对比指标。
- **可追溯**：每条回答带引用来源；拒答和追问有明确标记字段。
- **性能**：单次问答响应时间可接受（目标 10 秒内），文档入库为离线操作。
- **成本**：Embedding 用本地模型；LLM 调用记录 token 消耗，评估结果中体现。

## **7. MVP 范围**

**第一版只做动作技术一类的完整链路**：文档入库 → 意图分类（动作/疑似伤病/超范围）→ 检索问答 → 引用展示 → 安全拒答 → 评估脚本输出指标。

跑通后再接入营养和伤病预防两类，扩展分类与检索路由，评估集同步扩充。

**MVP 完成标准**：

1. 上传动作类文档后可问答，回答带引用；
2. 疑似伤病问题稳定拒答；
3. 评估脚本能按类别输出指标表；
4. 公网 HTTPS 可访问。

## **8. 评估设计**

评估集 25 到 30 条，分布：

- 动作技术可答 8 条；
- 营养可答 6 条；
- 伤病预防可答 5 条；
- 跨类综合 5 条；
- 应拒答/引导就医 5 条；
- 应追问澄清 3 条。

指标：

- **检索命中率**：期望关键信息点是否出现在引用片段中；
- **答案覆盖率**：期望关键信息点是否出现在最终答案中；
- **安全拒答率**：应拒答问题中正确拒答的比例；
- **误拒率**：可答问题中被错误拒答的比例；
- **平均 token 消耗**：每次问答的 LLM token 用量。

## **9. 技术栈与架构要点**

- 后端 FastAPI；向量库 ChromaDB；Embedding 用本地 sentence-transformers；LLM 走 API。
- 分层路由：意图分类（规则 + 少量 LLM 调用）→ 按类限定检索目录 → 疑似伤病在检索前拦截。
- 部署：Docker + Gunicorn/Uvicorn + Nginx + certbot HTTPS，2 核 2G 轻量服务器。
- 开发方式：用 Trae 按垂直切片生成代码，每个切片跑通再进下一个。

## **10. 明确不做**

- 不做用户账号体系与训练计划长期跟踪；
- 不做多轮复杂对话记忆；
- 不做伤病诊断、康复方案、用药建议；
- 不做通用健身百科或开放域问答；
- 不承诺回答的医学准确性，文档内容注明来源，页面标注“仅供学习参考，不构成训练或医疗建议”。

## **11. 风险与应对**

**风险**

**应对**

安全机制过激导致误拒正常问题

评估集中加入可答问题，监控误拒率

文档质量参差、说法矛盾

每篇注明来源；矛盾处保留，作为检索与引用展示的素材

意图分类不准导致路由错误

先用规则 + 少量 LLM 调用，评估集按类别统计错误

伤病类问题被模型“绕过”边界回答

系统提示词 + 检索前拦截双保险；评估集专设应拒答用例
